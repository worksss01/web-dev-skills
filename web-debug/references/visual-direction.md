# From references to a coherent visual system

Use during substantial [website design](website-design.md), especially when a short brief calls for a distinctive product or brand experience. Keep the modern default and expanded-control requirements. This is a decision aid, not a prescribed style, dependency list or extra workflow for a small fix.

## Resolve the direction before collecting effects

Translate the brief into a short working direction: what the visitor should understand/do; a central visual subject; how type and that subject share the composition; the recurring surface/color/spacing rules; and the meaningful next state. Decide whether the work primarily needs an expressive launch, an editorial narrative or an operational interface. An operational screen can be visually distinctive without a cinematic background occupying task space.

For example, a fictional visual-material studio can let one original sculpture carry the opening, then let shape/material controls change that same object. An editorial page can derive its identity from scale, image sequencing and deliberate line breaks. A queue needs comparable records, selected context and a clear next action. These are different compositions, not one template with replacement copy.

Identify the hardest visual dependency early: an asset, rendering technique, crop, type treatment or interactive model. Resolve it in the first representative slice. A generic orb, stock photo or placeholder card is not an adequate substitute when the brief depends on a specific subject. Choose an original code-native scene when it communicates the product; do not introduce WebGL merely to signal sophistication.

## Choose references by the decision they inform

Use the dated [reference map](design-patterns.md#component-and-scene-libraries). Extract relationships rather than collecting unrelated attractive widgets: subject-to-type scale, depth ordering, alignment, contrast, motion timing and the transition into the next section. Distinguish a live component from a thumbnail, prerecorded preview or unverified vendor description.

For each selected mechanism, decide its role in this page and how it will be adapted. Keep a recognizable focal idea and subordinate supporting motion to it. Give subsequent sections deliberate changes in density or surface while preserving the same visual rules. Do not repeat the opening or mix incompatible button, shadow, radius and type systems from several libraries.

## Adapt components to the product

Inventory the existing stack and reusable components first. Align imported or authored pieces to the project's color roles, type scale, spacing, radii, border/shadow treatment and motion timing. Connect their values, loading/error states and responsive forms to actual task data. A decorative notification list is not evidence of a working notification system; a shader thumbnail is not proof that the effect runs on the target device.

Use existing licensed code when appropriate, or author the mechanism independently. Before copying/installing, verify the exact component/version, license, dependencies, server/client boundary and required assets against its current official documentation. A visual-reference link is not authorization to buy, connect an MCP server, run an installer or redistribute paid source/prompts. No account or library is required to follow this guide. Do not force a React library into another stack or silently copy a premium implementation.

## Choreograph change and preserve an available route

For meaningful motion, specify the input, changing property, retained identity and settled state. Tie motion to understanding: selection changes the subject; progression reveals a relationship; new records enter without displacing the primary task unexpectedly. Set responsive composition and reduced-motion behavior alongside the animated version.

For rendered scenes, choose a task-appropriate resource budget. Bound drawing resolution and work, suspend animation when hidden/offscreen and provide a pause control for continuing nonessential motion. Prefer event-driven redraws when idle. Preserve readable content and useful task controls if rendering fails; explain any unavailable live preview honestly. A static fallback can still be carefully art-directed and contemporary. Test the chosen fallback deliberately instead of assuming it works.

## Compare at the level of craft

Review a wide/narrow opening, a meaningful continuation and relevant active states against the intended direction. Assess the actual subject, text/media hierarchy, material/light consistency, optical alignment, section rhythm and control finish. Then review behavior, keyboard/focus and failure cases separately. Correct the largest observed weakness before adding another effect. Measure frame cost or target-device performance when relevant; do not repeat a vendor's performance claim as your result.

Record the brief, selected reference mechanisms, adaptation, asset/code provenance, tested states and limits in the existing task evidence. Author walkthroughs establish what was built and checked, not that the skill reliably improves every model. Use comparable fresh tasks before claiming broad generation gains.
